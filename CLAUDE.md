## Project

Tio Minuter is a single-module (`:app`) Android workout app written in Kotlin with Jetpack Compose and Material 3. It walks the user through a daily routine of TIME- and REPS-based exercises, showing GIF animations, a countdown timer, and sound/haptic feedback. The package is `com.javargasp.tiominutermvi`. Dependency versions live in `gradle/libs.versions.toml`. The Compose BOM (2026.09.00) resolves Compose UI 1.12.1 and Material3 1.4.0; `material-icons-core` is a direct dependency because material3 no longer pulls it transitively. **Rule: the Compose BOM must cover the Compose version resolved at runtime; check both compile and runtime classpaths (`./gradlew :app:dependencies --configuration debugCompileClasspath` / `debugRuntimeClasspath`) after any dependency upgrade.** Also check the Kotlin metadata of new libraries: Kotlin 2.2.10 reads metadata up to 2.3 (that is why Firebase BoM is 34.19.0 and googleid 1.2.0, see "Accounts").

The app reads its content through a single read path that prefers a verified download from Firebase Hosting over the bundled copy, described in "Remote content" below. The app also has an isolated **Program** feature (multi-week generated programs), described in "Program feature" below, a unified **training history** of every completed workout, described in "Training history" below, a **weekly goal** with progress on Home, described in "Weekly goal" below, **logging an activity** done outside the app's routines, described in "Log an activity" below, **training photos** attached to history entries (local only), described in "Training photos" below, **accounts** (Google sign-in with Firebase Auth, or guest mode), described in "Accounts" below, **groups** (friends compare their week: ranking, invite codes, an "already trained today" banner on Home; signed-in accounts only), described in "Groups" below, and a **group feed** (finished workouts shared in my groups, with reactions and a thumbnail), described in "Feed" below. The **daily routines unlock one by one** (and can be restarted), synced so the phone and the web agree, described in "Daily unlock" below. Workout names are resolved in the viewer's language by one resolver, described in "Workout names" below. A **Flutter web app** (`web/`, served at the Hosting root) lets a signed-in person view their week, history and groups and react in the feed, described in "Web" below. A signed-in account's training log, weekly goals, programs and daily progress are **synced with Firestore** (offline-first: Room stays the only source of truth for the UI), described in "Sync" below, on the model and rules of "Firestore".

`.coda/docs/TECHNICAL_SUMMARY.md` is a detailed hand-off doc covering per-screen state, intents and effects, the gym data flow, tests and known tech debt. Keep it in sync with this file.

## Content

`content/` at the repository root is the single source of the app's content (Android now, the Flutter web app later). Editing guide: `content/README.md`.
- **Folder.** `content/v1/`: `exercises.json`, `routines.json`, `routines_for_gym.jsonc`, `program_exercises.json`, `program_templates.json` and `animations/*.gif` (moved from `app/src/main/assets` with `git mv`, history kept). `v1` is the format today's app reads; a change older apps can't read goes to a new `content/v2/`. The unused `routines.jsonc` is archived in `docs/archive/`.
- **APK.** `app/build.gradle.kts` sets `android.sourceSets["main"].assets` to `../content/v1`, so the APK bundles the same files at the same asset paths as before (`exercises.json`, `animations/1_jumping_jack.gif`…); the app reads them only through `ContentSource` / `AnimationLocator` (see "Remote content"), which fall back to these bundled assets. `androidResources.ignoreAssetsPatterns += "!manifest.json"` keeps the generated manifest out of the APK. There is no `app/src/main/assets` any more.
- **Tests.** Every unit test that reads content uses `testutil.CONTENT_DIR` (`File("../content/v1")`): `GymDataValidationTest`, `DailyDataValidationTest`, `ProgramCatalogValidationTest`, `ProgramTemplatesValidationTest` and `ProgramTestAssets` (generator, focus, BALANCED regression, rules tests). `NeutralLanguageTest` and `ProgramPerSideTextTest` read `src/main/res`, not content.
- **Validation gate** (`.github/workflows/content-validate.yml`, pull requests and non-main pushes touching `content/**`; reusable): JDK 17, `./gradlew :app:testDebugUnitTest --tests "*ValidationTest" --tests "com.javargasp.tiominutermvi.domain.program.*"` (the data validation tests plus the program tests on the real templates). Note: `gradle/gradle-daemon-jvm.properties` asks for a Java 21 daemon, which Gradle finds on the runner or downloads.
- **Daily minimum duration.** Every daily routine must reach the 10-minute counting rule (see "Weekly goal") for a person who does every slot: its **conservative minimum active time** is ≥ 10.5 minutes, and the content aims at ≥ 11 (1 minute of margin). The estimate is `DailyDurationEstimate.conservativeMinimumSeconds` (unit-test source, `data/remote/`), the only definition, following what `WorkoutViewModel` counts: TIME = `amount` + 5 s Get Ready, rest = `amount`, REPS = 2 s per rep, no transitions. `DailyDataValidationTest` fails below `MIN_COUNTED_DURATION_SECONDS + 30`. Days 1–7 and 9 were lengthened for it (warm-up, a rest after the third exercise, longer holds, and a short second round on days 1–5; TECHNICAL_SUMMARY §0 has the table).
- **Manifest.** `python3 scripts/build_manifest.py` (standard library) writes `content/v1/manifest.json`: `schemaVersion` 1, `contentVersion` (UTC `yyyyMMddHHmmss`, `--content-version` to fix it) and every file's `path`, `size`, `sha256`, sorted by path (itself and hidden files excluded). Generated in CI, gitignored (`content/*/manifest.json`), never in the APK.
- **Publishing** (`.github/workflows/content-deploy.yml`, workflow "Hosting deploy"): a push to `main` touching `content/**`, `web/**`, `shared/**`, `firebase.json` or `scripts/stage_hosting.py` runs the content gate and the web gate (`web.yml`), builds the web app (Flutter 3.47.7), `build_manifest.py`, `scripts/stage_hosting.py`, then `FirebaseExtended/action-hosting-deploy@v0` (`channelId: live`, `projectId: tiominuter-e43f7`, secret `FIREBASE_SERVICE_ACCOUNT_TIOMINUTER_E43F7`; Hosting only). Other code changes never deploy. One deploy at a time (`concurrency`).
- **Hosting** (`firebase.json`, `.firebaserc` → `tiominuter-e43f7`): public folder `hosting/public/` (generated, gitignored, replaced as a whole), filled by `scripts/stage_hosting.py` (also the hosting `predeploy` step): `web/build/web/` at the root (it stops without a web build; `main.dart.js` is renamed `main.dart.<sha256 prefix>.js` and `flutter_bootstrap.js` pointed at it, the only long-cached file, since Flutter doesn't hash its names) and every `content/v<N>/` under `content/v<N>/` (no hidden files, no README; it stops when a manifest is missing). URLs: the web app at `https://tiominuter-e43f7.web.app/`, the content at `/content/v1/<file>`. Rewrites: every path except `/content/**` and the reserved `/__/**` → `/index.html` (`"!/@(content|__)/**"`: a missing content file is a 404, never the app; `/__/auth/handler`, `/__/auth/iframe` and `/__/firebase/init.json` stay Firebase's — production serves them before rewrites anyway, the Hosting emulator didn't). Headers: `no-cache` by default (`index.html` on every app route, `flutter_bootstrap.js`, `flutter_service_worker.js`, `version.json`, `manifest.json`); `main.dart.*.js` one year, immutable; `assets/`, `canvaskit/`, `icons/`, `flutter.js`, `favicon.png` one hour; `/content/**` keeps its own rules below (they come last in `firebase.json`, so they win).
- **App.** The app downloads the published `v1` at start and verifies it before use (see "Remote content"). A manifest that lists a file the app doesn't know (a new top-level file, an animation that isn't `animations/<name>.gif`) is rejected as a whole by the app, which keeps its content: add new kinds of files in `content/v2/`.
- **Cache rules** (`firebase.json` headers): `manifest.json` → `Cache-Control: no-cache`; other `.json` / `.jsonc` → `public, max-age=300` (`.jsonc` served as `application/json`); `.gif` → `public, max-age=31536000, immutable`; `Access-Control-Allow-Origin: *` on all of `/content`. **Never overwrite a GIF: a changed animation gets a new file name** (clients keep the old bytes for a year). Checked locally with the Hosting emulator.

## Architecture

The code is layered as `data/` → `domain/` → `ui/` and uses MVI throughout. Koin handles dependency injection (`di/ContentModule.kt`, `di/WorkoutModule.kt`, `di/ProgramModule.kt`, `di/AuthModule.kt`, `di/SyncModule.kt` and `di/GroupsModule.kt`, started in `TioMinuterApplication`), which also sets up a Coil `ImageLoader` with GIF decoding.

**MVI core (`ui/base/`).** Every screen ViewModel extends `BaseViewModel<Intent, State, Effect>`:
- The UI calls `handleIntent(intent)`, which launches `reduce(intent, currentState)` in `viewModelScope`.
- `reduce` calls `setState(...)` to update a `StateFlow`, and `sendEffect(...)` for one-shot events such as navigation, sound and haptics. Effects go through a `Channel`.
- Screens collect effects with `CollectEffects` (lifecycle-aware). `MviComposable(viewModel, onEffect) { state, onIntent -> }` bundles state collection and effect collection together.
- Two wiring styles coexist. `HomeScreen` wires state and effects by hand (and renders the stateless `HomeContent(state, onIntent)`, which the previews in `HomePreviews.kt` use); `DailyRoutineSelectionScreen` and `WorkoutScreen` use `MviComposable`.
- `ui/example/` holds the reference template.
- A feature is a `ui/<feature>/` folder containing `*Intent`, `*State`, `*Effect`, `*ViewModel` and `*Screen`. Each ViewModel must be registered in `WorkoutModule`.

**Data.** The network is used by the content sync (see "Remote content"), Google sign-in (see "Accounts") and the Firestore sync of a signed-in account (see "Sync"). Both flows are offline-first: a simulated remote source (the content files, through `ContentSource`) fills Room, and the repositories read only from Room. The daily flow stores only its catalog; there is no daily progress.
- The domain models `Routine`, `RoutineExercise`, `Exercise` and `ExerciseType` are still `@Serializable` (with the custom `ExerciseTypeSerializer`), but only `SerializationTest` decodes them now. The app decodes DTOs.
- A `RoutineExercise` points to an `Exercise` by `exerciseId`. Its `amount` means seconds for `TIME` and target reps for `REPS`. `isRest` (default `false`) marks a rest slot; only the daily mapper sets it.
- `Exercise.animation` is a file name in `content/v1/animations/` (the asset folder `animations/`, see "Content"), loaded through `AnimationLocator` (the bundled `file:///android_asset/animations/<name>`, else a downloaded file).
- The old, unused `routines.jsonc` is archived in `docs/archive/` (not in the APK, not published).
- `GymDataValidationTest` and `DailyDataValidationTest` check the real assets: unique routineIds, known exerciseIds, valid types and values, and that every animation a routine uses exists. The daily test also checks that every routine has at least one exercise. Both read `content/v1` by relative path through the shared `testutil.CONTENT_DIR` (`../content/v1`), so they must run from the `app/` module directory (Gradle does this).
- Every exercise used by `routines.json` or `routines_for_gym.jsonc` has its animation file. `exercises.json` still names 12 files that don't exist (exercises 26, 27, 33, 35–37, 39, 41–45), but only the archived `routines.jsonc` references those exercises.

**Simulated remote sources (`data/remote/`).** `AssetGymRemoteDataSource` and `AssetDailyRemoteDataSource` treat the content files as fake endpoints, read through `ContentSource` (the name "Asset" stayed; they no longer touch the assets).
- Both go through the shared helpers in `RemoteAssets.kt`:
  - `fetchEndpoint` waits `simulatedLatencyMs` (default 0), reads a `ContentJsonFile` through `ContentSource` and decodes it with that file's decoder, on `Dispatchers.IO`.
  - `fetchExerciseCatalog` is the single implementation of `fetchExercises()` for both sources; `EXERCISES_FILE` names its file.
- Both decode with the shared `remoteJson` (comments, trailing commas and unknown keys allowed). Each file and its decoder is a `ContentJsonFile`: `EXERCISES_CONTENT` (`RemoteAssets.kt`), `AssetDailyRemoteDataSource.DAILY_ROUTINES_CONTENT`, `AssetGymRemoteDataSource.GYM_ROUTINES_CONTENT`; the content sync decodes downloads with the same objects.

**Gym Routines data.** `data/remote/GymRemoteDataSource` simulates a backend. `AssetGymRemoteDataSource` reads `assets/routines_for_gym.jsonc` and `assets/exercises.json` and decodes them into DTOs in `data/remote/dto/`. These DTOs are kept separate from the domain models, and `type` stays a raw `String` until the mappers in `data/mapper/` convert it. In the gym JSON, `"set"`/`"rest"` map to `sets`/`restSeconds`, and for `TIME` each value in `reps` is a duration in seconds.
- Catalog: 11 routines (64 Pull Day, 65 Push Day, 66 Leg Day, 67 Arms Day, 68 Shoulder and Leg Day, 69 Back, 71 Chest, 72 Glutes & Legs, 73 Legs & Core, 74 Full Body A, 75 Full Body B). Never modify existing routines (their progress is cleared when their slots change); add new ones with free ids. `"set"` must equal the size of `"reps"`.
- The gym screens have no per-side support: new routines must not use exercises that `program_exercises.json` marks `perSide` (older routines 64 and 66 do).
- `exercises.json` also has 116 Barbell Bench Press and 117 Romanian Deadlift (same ids and GIFs as `program_exercises.json`).

**Catalog names (shared by the three catalogs).** `name` / `routineName` are English and required; the Spanish name sits next to it: `nameEs` in `exercises.json` and `program_exercises.json`, `routineNameEs` in `routines_for_gym.jsonc`.
- `exercises.json`: every entry has `nameEs`. For an id that is also in `program_exercises.json` it is exactly that entry's `nameEs` (`GymDataValidationTest` checks it). Names usually said in English in Spanish gyms stay as they are ("Burpees", "Hip thrust", "Face pull en polea", "Contractor de pecho (pec deck)", "Skipping (rodillas altas)", "Sentadilla hack", "Pullover con mancuerna").
- In the DTOs they are optional (`ExerciseDto.nameEs`, `GymRoutineDto.routineNameEs`, default null), so JSON without them still decodes. Room stores them in `exercises.nameEs` and `gym_routines.routineNameEs` (nullable, database v6); the domain has `Exercise.nameEs` and `GymRoutine.routineNameEs` (default null, so `SerializationTest` and older data keep working).
- Validation: every exercise used by a daily or gym routine has a non-blank `nameEs`, and every gym routine a non-blank `routineNameEs` (`DailyDataValidationTest`, `GymDataValidationTest`).
- Display rule: `localizedName(name, nameEs, language)` in `ui/components/LocalizedName.kt` is the only place that picks a catalog name: Spanish (`"es"`, any region) → `nameEs` when not blank, otherwise `name`; any other language → `name`. Composable overloads (`localizedName(name, nameEs)`, `Exercise.localizedName()`) read the language from `LocalConfiguration`. Exercise names use it directly; **gym routine names go through `WorkoutNameResolver`** (`GymRoutine.workoutName()`, see "Workout names"), whose rendering uses this rule. Never show `exercise.name` / `routineName` directly. The daily routine selection shows no exercise names. The Program feature keeps its own `displayName(spanish)` / `isSpanish()`.
- Exercise names are not string resources: the old `ex_*` strings (and `incline_dumbbell_curl`) were removed from `values` and `values-es`.

**Local database.** Room is the local source of truth for gym routines, the daily-routine catalog, the training history and the weekly goals.
- `data/local/TioMinuterDatabase` is at **version 11**, with schemas exported to `app/schemas/` (`1.json` … `11.json`) by the Room Gradle plugin. Never edit an exported schema of a released version. Entities live in `data/local/entity/`, DAOs in `data/local/dao/`, and the `GymRoutineWithExercises` / `DailyRoutineWithExercises` relations in `data/local/`.
- Migrations: v1 → v2 is an `AutoMigration` that only adds `daily_routines` and `daily_routine_exercises`; v2 → v3 is an `AutoMigration` that only adds `training_log`; v3 → v4 is an `AutoMigration` that only adds `weekly_goal`; v4 → v5 is an `AutoMigration` with the spec `TioMinuterDatabase.Migration4To5` (`@RenameColumn`) that renames `weekly_goal.daysPerWeek` to `workoutsPerWeek`, keeping the values; v5 → v6 is an `AutoMigration` that adds the nullable `exercises.nameEs` and `gym_routines.routineNameEs` (null until the next catalog refresh, which upserts them; gym progress is kept because the slots don't change); v6 → v7 is an `AutoMigration` with the spec `TioMinuterDatabase.Migration6To7` that adds `gym_session` and, in `onPostMigrate`, gives every routine with progress in flight (some but not all slots completed) a session from its completion times: the latest run without a gap over the inactivity timeout (`GymSessionRules.fromCompletionTimes`), so an exercise done days earlier doesn't stretch it; fully completed routines get none (their entry was already recorded); v7 → v8 is an `AutoMigration` that only adds `daily_session` (the daily workout's active-time session; nothing to derive, the old daily time lived in memory); v8 → v9 is an `AutoMigration` that only adds `sync_outbox` (see "Sync"); v9 → v10 is an `AutoMigration` that only adds `feed_share` (the group feed's queue, see "Feed"); v10 → v11 is an `AutoMigration` that only adds `daily_progress` (one row; created on its first read from the history, see "Daily unlock"). Other tables are unchanged. There is no `fallbackToDestructiveMigration`. Each future schema change needs a new version, an exported schema and a migration plus a `MigrationTest` case.
- `GymRoutineDao.replaceCatalog` is the single write path for the gym catalog: it upserts routines (never delete-and-reinsert, so progress is not cascaded away), deletes disappeared routines (CASCADE), and replaces each routine's exercise slots. `GymExerciseProgressEntity` has a FK to the routine only, so progress survives exercise refreshes, but writing progress for a routine that no longer exists throws.
- Daily catalog: `DailyRoutineEntity` (`daily_routines`: routineId PK, routineDay, title?) and `DailyRoutineExerciseEntity` (`daily_routine_exercises`: PK (routineId, position), raw `type` string, `amount`; FK to `daily_routines` with CASCADE; index on `exerciseId` with no FK to `exercises`). Exercise data reuses the shared `exercises` table (`ExerciseEntity`/`ExerciseDao`).
- `DailyRoutineDao` provides `observeRoutinesWithExercises`, `getRoutinesWithExercises`, `getRoutineWithExercises` (both lists ordered by routineId), `countRoutines` and a `replaceCatalog` with the same semantics as the gym one. `ExerciseDao` also has `getAll()` (ordered by exerciseId) and `getById(id)` for the daily repository.
- Daily and gym refreshes both upsert the shared `exercises` table from the same `exercises.json`. Rows are never deleted, so neither refresh can remove an exercise the other one needs.
- `room-testing` (androidTest only) requires kotlinx-serialization ≥ 1.8.1, and AGP pins the test classpath to the app's version. That is why `kotlinxSerialization` is 1.8.1 in the catalog.

**Offline-first gym flow.** `GymRemoteDataSource` → mappers in `data/mapper/` → Room → repositories → `Flow` → gym ViewModels.
- `GymRoutineRepositoryImpl.refresh()` fetches routines and exercises from the remote source. It writes everything in one `database.withTransaction` (upsert exercises, then `replaceCatalog`), guarded by a `Mutex`. On failure the database is untouched.
- Inside that transaction, a routine's progress is cleared only when its exercise slots changed (exerciseId, type, reps, restSeconds, in order). Unchanged routines keep their progress.
- `GymProgressRepositoryImpl` owns completion markers. Their `completedAt` timestamp comes from an injected `WallClock` (`domain/time/`); `getCompletionTimes(routineId)` returns them (no longer used for the duration: see "Workout sessions").
- The app reads only from Room. `observeGymRoutines`, `observeGymRoutine` and `observeCompletedPositions` return mapped domain models. A slot with an unknown type string is skipped, and a missing exercise maps to `exercise = null`, which the UI shows as "Unknown exercise".

**Offline-first daily flow.** `DailyRemoteDataSource` → mappers in `data/mapper/DailyMappers.kt` → Room → `WorkoutRepositoryImpl` → `HomeViewModel`, `DailyRoutineSelectionViewModel`, `WorkoutViewModel`. The `WorkoutRepository` read signatures are unchanged.
- `WorkoutRepositoryImpl(database, dailyRemoteDataSource)` keeps its class name; it is a Koin `single`, so its state lasts for the process.
- `refresh(): Result<Unit>` (on the interface) fetches routines and exercises. It writes them in one `database.withTransaction` (upsert exercises, then `DailyRoutineDao.replaceCatalog`), guarded by a `Mutex`. On failure the database is untouched.
- **Refresh once per process:** the first call to any read method (`getRoutines`, `getRoutine`, `getExercises`, `getExercise`) runs `refresh()` once. Concurrent first readers wait for that single refresh; later reads go straight to Room.
- **If that refresh fails:**
  - When Room already has routines, it logs a warning (`Log.w`, tag `WorkoutRepository`) and serves the stored data.
  - When Room is empty, the read throws, so the ViewModels show their existing error or fallback (Home shows "Day 1"). The next read tries the refresh again.
- `getRoutine` and `getExercise` read single rows. Nothing re-reads the assets.
- The mappers set position = index in the DTO list and sort slots by position. A slot with an unknown type is skipped and logged with `println`, like the gym mappers. They reuse the exercise mappers and `toExerciseType` from `GymMappers.kt`.
- Rest is identified only in `DailyMappers.kt`: a slot whose `exerciseId` equals `DAILY_REST_EXERCISE_ID` (13, the "Rest" entry of `exercises.json`) maps to `RoutineExercise.isRest = true`. No other code knows the rest id.
- `AssetDataSource` is no longer registered in Koin nor used by app code (the Koin `Json` that fed it was removed); only `AssetDataSourceTest` uses it.

**Navigation (`ui/navigation/AppNavigation.kt`).** Route constants and builders live in `Routes`. `AppNavigation(startDestination)`: `MainActivity` passes `welcome` until a start choice is stored, else `home`, read synchronously from `AuthPreferences` before `setContent` (no flicker; see "Accounts"). Welcome → `home` pops `welcome`; Account: `home` → `account`. Daily flow: `home` → `daily_routine_selection` → `workout/{routineId}` → `workout_completion/{routineId}` (`Routes.workoutCompletion(id)`: the day just finished; "Start again from Day 1" → `daily_routine_selection` above `home`). History: `home` → `training_history` (see "Training history"). Goal: `home` → `weekly_goal` (see "Weekly goal"). Activities: `home` or `training_history` → `log_activity`, and `training_history` → `log_activity/{entryId}` (see "Log an activity"). `WorkoutViewModel` gets `routineId` as a Koin parameter, via `koinViewModel { parametersOf(routineId) }` in `WorkoutScreen` and `viewModel { (routineId: Int) -> ... }` in the module. `WorkoutCompletionScreen` uses `MviComposable` with `WorkoutCompletionViewModel(routineId, workoutRepository, dailyProgress)` (only for "Start again from Day 1" after the last day) and renders the stateless `WorkoutCompletionContent`.

**Program navigation.** Home's third button, the `OutlinedButton` "Programs", → `HomeIntent.OnProgramsClicked` → `HomeEffect.NavigateToProgramList`. ## Remote content

The content published on Firebase Hosting (`BuildConfig.CONTENT_BASE_URL` = `https://tiominuter-e43f7.web.app/content/v1/`) reaches the app without a release. With no network the app works exactly as before on the bundled content. Core package `data/content/`, Koin `contentModule` (`di/ContentModule.kt`, started first). Only permission added: `INTERNET`.

**Read path rule.** Content JSON is read only through `ContentSource` (`readText(path)`, `read(ContentJsonFile)`), and animations only through `AnimationLocator` (via `ExerciseAnimation`). Never read the assets or build a `file:///android_asset/...` URL anywhere else.
- `CachedContentSource`: the cached file of the active version when it is listed and stored with its size, else the bundled asset. Cached JSON is used only when the local manifest's `bundleFingerprint` (`BundledContentHashes`: sha256 of every bundled content JSON) matches this APK, so an app update with newer bundled content is never shadowed by an older download (the next sync re-activates against the new bundle).
- `ContentAnimationLocator`: the bundled asset first, then the cached file, else null (Coil shows nothing, as for a missing asset). Cached files are named by hash, without extension; Coil's GIF decoder detects the format from the bytes.
- `ActiveContent` reads the local manifest once per process (the syncer touches it before it changes anything), so **a version activated by a sync is used from the next launch**; repositories keep their refresh-once-per-process behaviour.
- `ContentJsonFile(path, deserializer, json)` is a content file with the decoder the app uses. Every one is registered in Koin with `named(path)` (core ones in `contentModule`, program ones in `programModule`); their paths are the only top-level JSON files a manifest may list. A new content JSON file needs its `ContentJsonFile` registered.

**Sync** (`ContentSyncer.syncOnce()`, launched once per process by `TioMinuterApplication` on its application scope, `Dispatchers.IO`; never blocks start or UI; the result is logged with `Log.i` / `Log.w`, tag `TioMinuterApplication`; no user-facing error):
1. Start: delete `staging/` leftovers and stored files the active manifest doesn't list (`ContentStore.cleanUp`, only at start so the running process never loses a file it uses).
2. GET `manifest.json` (≤ 1 MB, `ContentHttpClient` = `HttpUrlConnectionContentHttpClient`, HTTPS only, 10 s connect/read timeouts). Reject it when malformed, `schemaVersion != 1`, or any entry is invalid (`ContentRules.rejectionReason`: relative path, no `..`, no leading `/`, no `\`, only the known JSON files or `animations/<name>.gif`, size ≤ 5 MB, sha256 64 lowercase hex, no duplicates). Same `contentVersion` as the active one (with a matching fingerprint) → up to date, nothing downloaded.
3. Pick: JSON whose sha256 differs from the bundled asset's (hashed at runtime); animations not bundled. **A bundled animation is never downloaded**, so a changed animation must get a new file name. A file already stored with the same hash is reused.
4. Download into `staging/`, checking size and sha256; decode every JSON the version serves from the cache with its `ContentJsonFile`. Any failure → `Failed`, staging deleted, previous version untouched.
5. Activate: move files into `objects/<sha256>` (never overwrites a file in use), then write `active.json` LAST (temp file + fsync + rename). A crash in between leaves the previous version active; the moved files are orphans removed at the next start.

**Storage.** `filesDir/content/` (`ContentStore`, plain java.io): `objects/<sha256>`, `staging/`, `active.json` (`LocalContentManifest`: contentVersion, bundleFingerprint, the cached files only). Excluded from auto backup (`backup_rules.xml`) and from cloud backup and device transfer (`data_extraction_rules.xml`).

**Tests.** JVM: `ContentRulesTest` (allowed paths, schema, sizes, hashes, duplicates), `ContentSyncerTest` (real bundle `content/v1` + fake Hosting + temp folder: offline → bundled; same version → only the manifest is requested; changed JSON activated and served from the next launch; sha256 mismatch, longer body, > 5 MB, undecodable JSON → previous version stays; invalid paths reject the manifest; new animation downloaded and located, bundled one never requested; crash before the local manifest → previous version on restart and orphans cleaned; app update with other bundled JSON ignores the cache; once per process). Test doubles in `ContentTestDoubles.kt`. The data-source tests mock `ContentSource`.

## Training history

Every completed workout, wherever it comes from, becomes one entry in a single local history (foundation for weekly goals, logged activities and the future sync).

**Domain (`domain/traininglog/`).**
- `TrainingLogEntry(id, uuid, dateLocal "yyyy-MM-dd", completedAt, source, refId?, title, durationSeconds?, activityType?, intensity?, note?, photoPath?, createdAt, updatedAt)` and `enum TrainingSource { DAILY, GYM, PROGRAM, ACTIVITY }`. `ACTIVITY` entries are logged by hand (see "Log an activity") and use `activityType`, `intensity` (codes) and `note`. `photoPath` is the relative path of the entry's photo, if any (see "Training photos"). The source was called `FREE` until story 3; it was renamed because "free" reads as "free of charge" (no FREE row was ever written; `TrainingSourceRenameTest` pins that nothing refers to it). Derived: `activity`, `intensityLevel`, `isActivity`.
- `uuid` is a random UUID created with the entry (future sync id). `dateLocal` is the local date of `completedAt` in the device zone at that moment.
- `LocalDateProvider(WallClock, timeZoneProvider)`: `dateOf(millis)`, `today()`, `todayPlusDays(n)` (calendar days, DST-safe), and week helpers `mondayOf(date)`, `currentWeekStart()`, `weekDates(date)`, `previousWeek(date)`, `nextWeek(date)`, with `SimpleDateFormat`/`Calendar` (no `java.time`); the zone is read on every call. The week helpers delegate to the pure `CalendarDates` object (date-only arithmetic in UTC, weeks start on Monday, an invalid date throws `IllegalArgumentException`).
- `TrainingLogRecorder.record(source, refId, title, durationSeconds): Long` (the new entry's id) is the only thing other features use. `recordSafely(...): Long?` catches and logs (with `println`) any failure except cancellation and returns null then, so recording never breaks a workout; the id lets a completion attach a photo. `durationBetweenCompletions(times)` = last − first in seconds, null with fewer than two.
- `TrainingLogRepository`: `observeEntries()` (newest first), `observeEntriesBetween(fromDate, toDate)` (inclusive), `getEntry(id)`, `addActivityEntry(input)`, `updateActivityEntry(id, input)` (keeps the photo), `deleteEntry(id)` (also deletes the entry's photo files, after the row), `setPhotoPath(id, path?)` (returns the previous one, updates updatedAt; only the photo repository calls it) and `getPhotoPaths()`. `TrainingLogDao` has `getById`, `@Update update`, `updatePhotoPath(id, photoPath, updatedAt)` and `getPhotoPaths()` for them.

**Data.** `TrainingLogEntity` (`training_log`: autoincrement id, unique index on `uuid`, index on `dateLocal`, `source` as the enum name, no FKs) and `TrainingLogDao` (`insert` aborts on a duplicate uuid; `observeAll` / `observeBetween` ordered by completedAt desc, then id desc; `delete`). `data/traininglog/TrainingLogMappers.kt` (an unknown stored source is skipped and logged) and `TrainingLogRepositoryImpl(dao, WallClock, LocalDateProvider, TrainingPhotoFiles, newUuid)`, which also implements `TrainingLogRecorder`; its insert runs in `NonCancellable` so a ViewModel cleared right after a workout doesn't lose the entry. Koin (`workoutModule`): one `single` bound as both `TrainingLogRepository` and `TrainingLogRecorder`, plus `LocalDateProvider`.

**Where each source records.**
- DAILY: `WorkoutViewModel.finishWorkout` (the single `NavigateToCompletion`, also when every exercise was skipped), after sending the effect, in its own coroutine. refId `dailyRefId(routineId)` = `daily:<routineId>`, title `dailyWorkoutTitle` = `routineDay` (+ " · title" when present), duration = the workout's **active time** (on screen, background excluded; see "Workout sessions"). A daily workout left unfinished is recorded after 2 hours of inactivity.
- GYM: through the gym session (see "Workout sessions"). On full completion, `GymRoutineViewModel` calls `completeSession` when `showRoutineCompleted` turns true (non-empty routine fully completed), before the dismiss reset; it records only while the session exists and removes it in the same transaction, so re-sent `OnLoad`, rotations, later emissions and a dialog shown again after process death never record twice. An abandoned session (2 hours without a set) is recorded when it is closed. refId `gymRefId(routineId)` = `gym:<routineId>`, title = the routine's English `routineName` (the history shows the localized name at display time), duration = the session's last set − first set.
- PROGRAM: `ProgramRepositoryImpl`, after the progress is stored. Strength: when `markSlotCompleted` is the call that completes the workout (re-marking a slot of a completed workout doesn't record; reset + redo records again), duration = the strength session's first → last set. Cardio: every `markWorkoutCompleted`, with the screen's active time (treadmill and circuit: running and visible; outdoor run: the stopwatch, pauses excluded). Abandoned program sessions are recorded after 2 hours of inactivity (see "Workout sessions"). refId `program:<programId>:<week>:<dayIndex>`, title from `ProgramWorkoutTitles` in the current language.

**History screen (`ui/traininglog/`).** Route `training_history`; reached from the "See history" text button inside Home's weekly goal card → `HomeIntent.OnHistoryClicked` → `HomeEffect.NavigateToTrainingHistory` (Home has no separate History button). A FAB ("Log activity") opens `log_activity`; tapping an ACTIVITY entry opens `log_activity/{entryId}` (`OnEntryClicked` → `NavigateToEditActivity`); automatic entries (daily, gym, program) are not editable. `TrainingHistoryViewModel(repository, weeklyGoalRepository, localDateProvider, names: WorkoutNameCatalogs, photos)` observes entries, goals and the workout-name catalog (`state.names`; plus one lookup per PROGRAM entry) once in `init` and groups entries by week (`TrainingWeek` with that week's `WeeklyProgress`) and by `dateLocal` (`TrainingDay` with `DayLabel.Today` / `Yesterday` / `Date`). Each week starts with a header "Week of 13 October · 3 of 4 workouts ✓" (counted workouts and the goal in force that week; "· 3 workouts" before the first goal; TalkBack reads "goal met" instead of ✓). Headers are formatted with `DateFormat.getBestDateTimePattern(locale, "EEEEdMMMM")` ("Monday, 19 October" / "lunes, 19 de octubre"), times with the device 12/24-hour format. Rows: decorative source icon (an ACTIVITY entry shows its activity icon), title (`state.nameOf(entry).text()`: `WorkoutNameResolver` in the viewer's language, see "Workout names"; the stored title only as the fallback), "Gym routine · 32 min" (an ACTIVITY entry shows "45 min · Moderate" and the first line of its note) (`training_history_duration_minutes` plurals, rounded down, at least 1, so a 9:50 entry shows "9 min"; only the source when the duration is unknown), "Doesn't count toward the goal" for entries under the minimum (see "Weekly goal"), time. Empty state text. Long press → delete confirmation; also exposed as `onLongClick` semantics and a custom accessibility action. A pending delete closes if its entry disappears; a delete failure is logged.

## Daily unlock

The daily routines unlock one at a time, on Android and the web, synced (`users/{uid}/dailyProgress/state`, docs/firestore-model.md "`daily_progress`"). Product rules (decided):
- **Day 1 is always available; day N + 1 unlocks when day N is FINISHED** (the workout reached its completion screen: `WorkoutViewModel.finishWorkout`, also when every exercise was skipped). **A session closed for inactivity unlocks nothing.** Finishing a day that isn't the newest unlocked one (a repeat, or one locked meanwhile by a restart) changes nothing.
- **Unlocked days stay available and can be repeated.** Locked days are listed with a lock and "Complete Day N to unlock" / "Completa el Día N para desbloquearlo" and can't be started (Android ignores the tap; the web shows the lock line for a locked day opened by its URL and ignores every action there).
- **Existing users:** the first read of a device with no stored progress starts it from the history: `lastCompletedDay` = the highest routineId among the DAILY entries (`daily:<N>`, Kotlin's `toIntOrNull`; capped at 999), cycle 0. New users start at 0. Idempotent: only while there is no row (Android) / document (web).
- **"Restart days"** (the selection's top bar once a day is done; the web's app bar) asks first: "Every day will be locked again and you'll start from Day 1. Your history, your weekly goal and your groups won't change." Confirm → `lastCompletedDay` 0, `cycle` + 1. Nothing else is touched.
- **After the last routine** (Day 30 today): the completion screen (only for that day) and the selection ("You completed every day!") offer **"Start again from Day 1"** — the same restart and dialog (Android `RestartDaysDialog`, web `confirmRestartDays`).
- **"Day X available"** (Android Home, the web Train hub) = `min(lastCompletedDay + 1, lastRoutineId)` (`DailyUnlockRules.nextAvailableDay`), replacing the old "highest routineId". Fallbacks: Day 1 when the routines (or, on the web, the progress) can't be read; none without routines.
- **Guests:** local only (Room), like any other data. **Signed in:** synced. **Conflicts:** keep the more advanced state — a higher cycle (a restart) wins over an older cycle; in the same cycle, the further day. No device clock is compared.

## Workout names

**Rule: workout names always go through `WorkoutNameResolver`; never display stored titles directly.** A training entry's `title` is written once, in the recording device's language (the gym routine's English name, "Day N", the program title of that moment), and synced as is; it is only the fallback. The name is resolved at display time, in the viewer's language. No user-data change: `trainingLog` keeps `title` + `refId`, no Room migration.

## Workout sessions (gym, program, daily)

Every recorded duration is **real and bounded**. Each workout runs in a session that closes on its own after **2 hours without activity** (`SESSION_INACTIVITY_TIMEOUT`, `domain/session/Session.kt`, the single definition), recording **one** entry with the time done so far, dated on the session's start. A workout half-done today and finished tomorrow is two workouts, never one of a day.

**Two ways to measure.**
- **Set to set** (gym, program strength): the session starts at the first completed set and every completed set updates `lastSetAt` / `lastActivityAt`; duration = last set − first set. Sets inside an exercise exist only in memory; the exercise screens report each one (non-last sets launched without delaying the next phase, the last one awaited before the exercise is marked).
- **Active time** (daily, program treadmill / circuit / outdoor run) **matches what the workout does**: `ActiveTimeMeter` (with `MonotonicTimeSource`) counts while the workout's **timer runs** (a countdown, the run's stopwatch) **in the foreground or the background, screen on or off**, because the timers keep running there. Excluded: explicit pauses and states waiting for the person with no timer (a daily TIME exercise before "Get Ready"; before Start; after the end). One untimed step counts only while its screen is visible: a daily **REPS** exercise (the person does the reps, then taps "Done"; nothing proves it in the background). Each ViewModel derives "timer running" (and, for Daily, "REPS on screen") from its state, so every start, stop and pause is followed. Leaving a workout stops it. Daily has no pause button, and leaving the screen is not a pause while a countdown keeps running. The session stores `startedAt`, `activeSeconds`, `lastActivityAt` (WallClock) and is saved every 5 s while counting (`ActiveWorkoutSession.CHECKPOINT_MILLIS`) and on every change and action; after a process death the time up to the last save counts. Activity = the timer running or a user action.

**Rules.**
- Inactive = strictly more than the timeout since the last activity; never when the clock moved back. Durations clamp at 0.
- **Lazy close, no background work** (no timers, services, alarms or WorkManager). Checks: every Home `OnStart` (app start, before the week is read again; Home runs every `InactiveSessionCloser` — gym, daily, program — without knowing the program code), every resume of the gym selection / routine, daily selection, program list / detail / strength screens, and the next activity in the same workout (a set, or the active-time screen coming back after more than 2 h: the old session is recorded and the count restarts from 0).
- **Starting a new active-time session of the same kind records an open one first** (one daily session at a time; one cardio session for all program cardio).
- An active-time session is stored at the first real action (daily: the first action in the workout; cardio: Start), so opening and leaving a workout records nothing; a workout left unfinished (or a killed process) is recorded after 2 hours with the active seconds saved last.
- **Close on inactivity:** gym → entry + routine progress reset; program strength → entry, the workout **left resumable** (slots kept, not marked completed: finishing it later is a new session); daily and cardio → entry with the active time (a cardio workout is not marked completed).
- **Normal finish records once:** gym → `completeSession` removes the session in the same transaction; program strength → `markSlotCompleted` takes and deletes the session in its own transaction; daily and cardio → the session ends (`finish`) and the screen records its final active time. Manual resets discard the session without recording.
- **Idempotent:** every session kind has one `SessionLock` (Koin singles): one `Mutex`, one transaction, `NonCancellable`; a failure rolls back, is logged with `println` and the next check retries. Program sessions live in `programs.db` and the entry in `tiominuter.db`, so a close removes the session first and writes the entry last inside the `programs.db` transaction (a failed entry rolls the removal back).
- The 10-minute rule still decides what counts. Screens announce closed sessions once: "Your unfinished workout was saved (1 h 05 min)." / "Se guardó tu entrenamiento sin terminar (1 h 05 min)." (`showSessionSaved` Toast; minutes as in the history: rounded down, at least 1).
- **A ViewModel test that leaves an active-time workout counting must stop it before the end** (back, pause or finish): the 5-s save would keep `runTest` draining virtual time.

**Code.**
- Core `domain/session/`: `SESSION_INACTIVITY_TIMEOUT`, `SessionRules` (`isInactive`, `durationSeconds`, `latestRun`), `SessionTransactions`, `SessionLock`, `ClosedSession` / `ClosedSessionNotices`, `InactiveSessionCloser`; active time: `ActiveSession`, `ActiveSessionStore`, `ActiveSessionTracker` (`start`, `update`, `finish`, `closeInactive`), `ActiveTimeMeter`, `ActiveWorkoutSession` (the ViewModel helper). Entries with their own end and date go through `SessionEntryRecorder` (`TrainingLogRepositoryImpl`).
- Gym: `domain/gymsession/` (`GymSessionTracker` on the core), `gym_session` (v7). Daily: `daily_session` (v8, `DailySessionEntity`, `DailySessionDao`, `DailyActiveSessionStore`), `dailyRefId` / `dailyWorkoutTitle` (`domain/traininglog/DailyRefId.kt`), Koin `named(SessionQualifiers.DAILY)`. Program: `ProgramStrengthSessions` + `StrengthSessionStore` and `programRefId` (`domain/program/repository/`), `ProgramStrengthSessionStore` / `ProgramCardioSessionStore` (`data/program/repository/ProgramSessionStores.kt`), tables `program_strength_session` and `program_cardio_session` (programs v3), `ProgramRepository.onStrengthSetCompleted` / `closeInactiveSessions` / `takeClosedSessions` (defaults for fakes), `ProgramRepositoryImpl.cardioSessions`, Koin `named(SessionQualifiers.PROGRAM)` / `PROGRAM_CARDIO`.

## Weekly goal

Each person sets how many **workouts** per week to do; Home shows the current week's progress, computed from the training history. Two workouts on the same day count as two.

**Counting rule (`domain/goal/WorkoutCounting.kt`).** `countsTowardGoal(entry)` is the single rule: an entry counts when `durationSeconds >= MIN_COUNTED_DURATION_SECONDS` (10 minutes, the only definition of the minimum) or when its duration is unknown (null). Shorter entries stay in the history but don't count. `countedWorkoutsPerDay(entries)` maps each date to its counted entries.

**Rules (`domain/goal/`, pure, in `WeeklyProgressCalculator`).**
- `WeeklyGoal(workoutsPerWeek 1..14 (WORKOUTS_RANGE), effectiveFromWeek)` where `effectiveFromWeek` is the Monday ("yyyy-MM-dd") of the week it starts. The goal of a week is the latest goal whose `effectiveFromWeek` ≤ that week's Monday (`goalForWeek`); null before the first goal. Setting a goal applies from the current week; past weeks keep theirs.
- Weeks run Monday to Sunday in the device zone (dates come from `training_log.dateLocal`, fixed at recording time).
- `WeeklyProgress(weekStart, goal?, workoutsPerDay)`: `workoutCount` = counted workouts of the week, `workoutsOn(date)`, `trainedDates`; `isGoalMet` = goal != null && workoutCount ≥ goal (exceeding it stays met).
- `streak(today, goals, workoutsPerDay)`: consecutive completed weeks before the current one with the goal met (counting back from last week, stopping at the first missed week or at the first goal's week); the current week adds 1 only once met and never breaks it. No goal → 0.
- `CurrentWeekSummary(today, progress, streak)` derives `workoutsNeeded`. There is no "no longer reachable" state: several workouts per day are possible.
- `ObserveCurrentWeek(weeklyGoalRepository, trainingLogRepository, localDateProvider)` combines `observeGoals()` and `observeEntries()` (through `countedWorkoutsPerDay`) into `Flow<CurrentWeekSummary>`; "today" is read on every emission. Koin `factory`.

**Data.** `WeeklyGoalEntity` (`weekly_goal`: PK `effectiveFromWeek`, `workoutsPerWeek` — `daysPerWeek` until v5 —, `updatedAt`), `WeeklyGoalDao` (`@Upsert`, `observeAll` ordered by week), `data/goal/WeeklyGoalRepositoryImpl(dao, WallClock, LocalDateProvider)`: `observeGoals()`, `setGoal(workoutsPerWeek)` (stores this week's Monday; same week replaces; outside 1..14 → `IllegalArgumentException`). Koin `single<WeeklyGoalRepository>`.

**Home layout and card** (`ui/home/HomeScreen.kt` → `HomeContent`, card in `WeeklyGoalCard.kt`; previews in `HomePreviews.kt` and `WeeklyGoalCardPreviews.kt`). `HomeViewModel(workoutRepository, observeCurrentWeek, authRepository, guestBanner, sessionClosers, dailyProgress)` keeps `HomeState.week` and derives `weeklyMessage` (`GoalMet`, `WorkoutsLeft(n)`; null without a goal). Every `OnStart` first closes inactive sessions of every kind (gym, daily, program; app start and every return to Home; see "Workout sessions"), then restarts the observation (`flatMapLatest`), so a new day or week is picked up when Home is shown again. Home order: a `TopAppBar` with only the account action (`AccountAvatar`: the Google photo when signed in, else the account icon; labelled "Account") → the guest banner when shown (see "Accounts") → mascot and title → `WeeklyGoalCompactCard` ("This week", shown once the first summary arrives) → "Day X available" (`home_day_available` with `HomeState.currentDayName` through `WorkoutNameResolver`: "Día 5 disponible"; the next unlocked day, see "Daily unlock") → Start (daily), Gym routines and Programs. The column scrolls when it doesn't fit and stays vertically centered otherwise. The card is a `Card` made `clickable` with the click label "Open weekly goal" (`weekly_goal_card_open`):
- With a goal: the title and "3 of 4 workouts" on one line (`weekly_goal_progress` plurals; it can read "5 of 4 workouts"), a `LinearProgressIndicator` capped at 100 %, seven day circles Mon–Sun (letters from `weekly_day_short_*`, "L M X J V S D" in Spanish; filled on days with counted workouts, with the number when 2 or more and a check for 1; today outlined), and one message line: "Goal met this week!" or "N workouts left to reach your goal", followed by " · Streak: 3 weeks" when the streak ≥ 1. The day row is one TalkBack sentence: "Monday 1 workout, Wednesday 2 workouts. Today, Friday: no workouts yet."
- Without a goal: "Set your weekly goal" and a "Set goal" button. Tapping the card or the button → `HomeIntent.OnWeeklyGoalClicked` → `HomeEffect.NavigateToWeeklyGoal`.
- Always: "Log activity" / "Registrar actividad" and "See history" / "Ver historial" `TextButton`s (≥ 48dp, in a `FlowRow` that wraps when they don't fit) at the bottom of the card → `HomeIntent.OnLogActivityClicked` (log an activity) / `HomeIntent.OnHistoryClicked` (the training history).

**Goal screen (`ui/weeklygoal/`, route `weekly_goal`).** `WeeklyGoalViewModel(weeklyGoalRepository, localDateProvider)` starts from the goal in force this week, or `WeeklyGoalState.DEFAULT_WORKOUTS` (3) without one. Intents `OnIncrement` / `OnDecrement` (stop at 14 and 1; `canIncrement` / `canDecrement`), `OnSave` (success → `setGoal` + `NavigateBack`; failure → `saveFailed`), `OnBackPressed`. ## Log an activity

Anyone can log a workout done outside the app's routines (own gym routine, running, yoga, basketball…); it counts toward the weekly goal like any other workout through `countsTowardGoal`, with no goal logic of its own. No migration: `training_log` already had the columns.

**Naming rule.** Never use "free" for this ("free of charge" in English): the source is `TrainingSource.ACTIVITY`. Code names are `LogActivity*` (`LogActivityScreen`, `LogActivityViewModel`, `LogActivityState`, `LogActivityIntent`, `LogActivityEffect`, `LogActivityPreviews`) in `ui/logactivity/`; never name a class just `ActivityScreen` / `ActivityViewModel` (confusion with `android.app.Activity`). UI texts: "Log activity" (buttons), "Log an activity" / "Edit activity" (titles); "Registrar actividad", "Registrar una actividad" / "Editar actividad".

**Domain (`domain/traininglog/`).**
- `enum ActivityType(code)`: OWN_GYM_ROUTINE, RUNNING, WALKING, CYCLING, SWIMMING, YOGA, PILATES, DANCE, TEAM_SPORT, RACKET_SPORT, MARTIAL_ARTS, HIIT, STRETCHING, OTHER; `enum Intensity(code)`: EASY, MODERATE, HARD. Stored by code (`fromCode`, unknown → null); labels come from strings at display time (`ui/logactivity/ActivityLabels.kt`: `activityTypeLabel`, `activityTypeIcon`, `intensityLabel`, `intensityDescription`), never stored.
- An ACTIVITY entry: `activityType`, `durationSeconds` (required), `intensity` (required), optional `note` (≤ 200, trimmed, blank → null), optional photo (`photoPath`, set by the photo repository), `refId` null. For OTHER the custom name (required, ≤ 40, trimmed) is the `title`; for the other types `title` is empty.
- Date window: `completedAt` from 00:00 six days ago (device zone) to now, never in the future; `dateLocal` comes from `completedAt` via `LocalDateProvider` like any entry. When editing, the entry's own day stays allowed even if it is older than the window.
- `ActivityEntryInput(type?, customName, durationMinutes?, intensity?, completedAt, note)` and `ActivityEntryRules` (pure): `DURATION_MINUTES = 1..600`, `NAME_MAX_LENGTH = 40`, `NOTE_MAX_LENGTH = 200`, `DAYS_BACK = 6`, `windowStart(localDateProvider)`, `validate(input, now, earliest): Set<ActivityEntryError>` (TYPE_MISSING, NAME_MISSING, NAME_TOO_LONG, DURATION_OUT_OF_RANGE, INTENSITY_MISSING, DATE_TOO_EARLY, DATE_IN_FUTURE, NOTE_TOO_LONG), `titleFor`, `noteFor`. The repository rejects an invalid input with `InvalidActivityEntryException(errors)`.
- `LocalDateProvider` gained `nowMillis()`, `startOfDay(date)`, `epochMillisAt(date, hour, minute)` and `timeOfDay(millis)` (`TimeOfDay(hour, minute)`), all in the device zone.
- Repository: `addActivityEntry(input)` (new uuid, createdAt = updatedAt = now), `updateActivityEntry(id, input)` (only ACTIVITY entries, otherwise `IllegalStateException`; keeps uuid and createdAt, updates updatedAt), `getEntry(id)`; deleting uses `deleteEntry`.

**Screen (`ui/logactivity/`, routes `log_activity` and `log_activity/{entryId}` with a `NavType.LongType` argument; `Routes.logActivityEdit(id)`).** `LogActivityViewModel(entryId?, repository, localDateProvider, photos)` (Koin: `viewModel { params -> LogActivityViewModel(params.getOrNull<Long>(), …) }`; the screen passes no parameter to create). State: `form` / `initialForm` (`LogActivityForm`: type, customName, durationText, intensity, date, hour, minute, note, photo: `FormPhoto` None / Stored(photoPath) / Staged(StagedPhoto)), `isProcessingPhoto`, `dayOptions`, `errors` (shown after the first Save, then they follow edits), `hasUnsavedChanges`, `showsShortDurationHint`, dialogs, `isNotFound` (missing or non-ACTIVITY id).
- Activity type: `FilterChip`s in a `FlowRow` with a decorative emoji icon (the app only has the core Material icons) and the label as text; OTHER shows a name field with a counter.
- Duration: quick chips 15, 30, 45, 60, 90 min plus a numeric field (digits only, ≤ 3); under 10 minutes it shows "It won't count toward your weekly goal (minimum 10 minutes)" (minutes from `MIN_COUNTED_DURATION_SECONDS`).
- Intensity: three segments (each described to TalkBack as "Easy: you can talk normally" etc.) with the three descriptions listed below.
- Date: chips Today, Yesterday and the 5 days before ("Mon, 13 Oct", `getBestDateTimePattern(locale, "EEEdMMM")`), plus the entry's own day when editing an older one; time picker (Material 3 `TimePicker` in a dialog, device 12/24 h) defaulting to now for today and 18:00 for a past day (a chosen time is kept when the day changes); future times are rejected.

## Training photos

A photo can be attached to a training-history entry as light evidence of a workout. **Local only**: the photo stays on the device that took it; only a small thumbnail goes to the group feed (see "Feed"). The web app does the same in the browser (see "Photos on the web" below).

**Where.**
- Gym: the "Routine completed!" dialog (`GymRoutineState.completionPhoto`; the entry id comes from `recordSafely`).
- Program: the strength "Workout completed!" dialog and the cardio finished view (`ProgramWorkoutFinished`) of treadmill, outdoor run and circuit. `ProgramRepository.observeCompletionEntryId(programId, week, dayIndex)` exposes the entry recorded by the latest completion of that workout in this process (null when a new completion starts or recording fails); the ViewModels `drop(1)` its first value, which belongs to an earlier completion. The interface default (fakes) emits null.
- Log activity: create and edit (see "Log an activity").
- History: entries with a photo show a 48dp thumbnail (tap: full screen). A long press on an automatic entry (daily, gym, program) opens a menu: Add / Change photo, Remove photo (with confirmation), Delete; the same actions are accessibility custom actions. ACTIVITY entries keep long press = delete and change their photo in their edit form.
- Not in the daily workout.

**Capture (no dangerous permission).** `rememberTrainingPhotoPicker` (`ui/components/photo/`): gallery = Android Photo Picker (`PickVisualMedia`, images only); camera = `TakePicture` writing into `cache/training_photo_capture/capture.jpg` shared through the FileProvider (`${applicationId}.trainingphotos`, `res/xml/training_photo_paths.xml`, cache path only). CAMERA is never requested (the merged manifest has none). The camera row is hidden when no app answers `IMAGE_CAPTURE` (`<queries>` in the manifest for API 30+). `TrainingPhotoChooser` = the bottom sheet (camera / gallery + privacy note) with the launchers registered even while hidden, so a result after recreation still arrives.

**Processing** (`TrainingPhotoProcessor`, implemented by `data/traininglog/photo/AndroidTrainingPhotoProcessor` on `Dispatchers.IO`): bounds only, then decode with `PhotoSizing.sampleSize` (largest power of two keeping the longest side ≥ the target: never the full-resolution bitmap), exact scale + EXIF orientation (AndroidX `ExifInterface`, all 8 orientations via `ExifTransform`), re-encode: photo longest side 1080 px, JPEG 70; thumbnail 400 px, JPEG 60 (from the photo). Small images are never upscaled. `Bitmap.compress` writes no EXIF block, so every metadata field (location included) is dropped. Writes go to a `.tmp` sibling and are renamed. Errors: `TrainingPhotoException(UNREADABLE_IMAGE | NO_SPACE (ENOSPC) | ENTRY_NOT_FOUND | FAILED)`; `OutOfMemoryError` becomes FAILED. The pure rules (`PhotoSizing`, `ExifTransform`, `TrainingPhotoPaths`) are JVM-tested.

**Storage.** `files/training_photos/<entry uuid>-<version>.jpg` and `…-<version>_thumb.jpg` (`TrainingPhotoPaths`). `photoPath` stores the relative photo path; the thumbnail path is derived (no schema change). `version` = attach time, so a replacement gets new names: it is written before the old files are deleted (a failed replace keeps the old photo) and Coil never shows a stale image. `isValidPhotoPath` guards paths read from the database (no "..", only `training_photos/<name>.jpg`). Staged photos: `cache/training_photo_staging/`.

**Lifecycle** (`TrainingPhotoRepository` → `data/traininglog/photo/TrainingPhotoRepositoryImpl(trainingLog, processor, files, wallClock)`): `stage(source)` (processes into staging; deletes the camera file afterwards, also on failure), `commit(entryId, staged)` (moves into place, sets photoPath, deletes the previous photo's files), `discard(staged)`, `attach` = stage + commit, `remove(entryId)` (clears photoPath, deletes files), `cleanUp()` (deletes photo files no entry references, plus staged/camera files older than an hour; returns the count). Commit, remove and cleanup share one `Mutex` and run in `NonCancellable`. `TrainingLogRepository.deleteEntry` deletes the entry's files. `TioMinuterApplication` runs `cleanUp()` at start on an application scope (logs the count). `TrainingPhotoFileStore(filesDir, cacheDir)` (plain java.io, JVM-tested) implements `TrainingPhotoFiles`; composables build it from the context (`rememberTrainingPhotoFiles`) so previews work. ViewModels call the repository through `photoAction { }` → `PhotoResult.Success / Failure(error)`.

**Errors and privacy.** Every photo error is a short Toast (`showTrainingPhotoError`, effects `ShowPhotoError` in each ViewModel): it stays visible over dialogs and after navigating back. A photo failure never breaks the workout flow or loses the entry. Where a photo is added: "Photos stay on this device for now. Location data is removed." / "Por ahora las fotos se guardan solo en este dispositivo. Se elimina la ubicación." (`photo_privacy_note`). `files/training_photos/` is excluded from auto backup (`backup_rules.xml`) and from cloud backup and device transfer (`data_extraction_rules.xml`).

**Accessibility.** Thumbnails: `contentDescription` "Workout photo, <date>" / "Foto del entreno, <fecha>" (`photoContentDescription`), click label "Open photo"; the viewer's close button is labelled; buttons and sheet rows are at least 48dp; progress lines are polite live regions.

**Photos on the web** (`web/lib/domain/photos.dart`, `platform/photos*.dart`, `ui/train/photo_widgets.dart`). Same behaviour as Android, in the browser: **the full photo stays in THIS browser** (as Android keeps it on the phone), **only its thumbnail goes to the feed**; no Firestore model or rules change (the post's `thumb` already exists).
- **Where:** every completion view (`CompletionView` → `EntryPhotoSection`: daily, gym, program strength, treadmill, circuit), Log activity create and edit (staged in the form, kept on Save, discarded with it), and the history (a 48 px thumbnail when this browser has the photo; tap → full screen). ## Accounts

Sign in with Google (Firebase Authentication) or guest mode (Phase 1). A signed-in account's data is synced with Firestore (Phase 2b, see "Sync"); guests sync nothing. Firebase project `tiominuter-e43f7`.

**Rules.**
- **Credential Manager only** (`androidx.credentials` + `googleid`, `GetSignInWithGoogleOption`); never the deprecated `GoogleSignInClient` / play-services-auth sign-in API. The server client id is the generated `R.string.default_web_client_id`, never hardcoded.
- **No Activity in repositories.** `ui/auth/GoogleIdTokenRequester` (created per screen with `rememberGoogleIdTokenRequester()`) is the only code that talks to Credential Manager: it returns a `GoogleTokenResult` (Token / Cancelled / NoGoogleAccount / NoNetwork / Failed; NoNetwork comes from a `ConnectivityManager` check, hence the `ACCESS_NETWORK_STATE` permission) and clears the credential state after a sign-out or deletion. ViewModels ask for a token with a `RequestGoogleToken` effect and receive it as an `OnGoogleTokenResult` intent; repositories only receive the ID token.
- **Only user cancellation is silent.** Every other auth failure shows a message and is logged once (`Log.w`, without PII: `describeAuthFailure` keeps the exception class, `type` and message, and strips emails and tokens; never log ID tokens, emails or names). `GetCredentialCancellationException` → nothing; `NoCredentialException` → no Google account; no network (`ConnectivityManager` check, `IOException`, `FirebaseNetworkException`) → no internet; anything else (other `GetCredentialException`s, a non-Google or unparsable credential, any `FirebaseAuthException`) → "Couldn't sign in with Google". The mapping lives in `ui/auth/GoogleCredentialMapping.kt` and `authFailureOf` in `FirebaseAuthRepository.kt` (TECHNICAL_SUMMARY §18.1.1 has the table). The same applies to the re-authentication before a deletion: a failed re-auth shows the message and deletes nothing. Debug builds append the exception's short class name to the snackbar (`authMessageText`, `BuildConfig.DEBUG`); release builds don't. Picker shown but sign-in fails → check the SHA-1 / Android OAuth client (`client_type` 1) in `google-services.json`.
- **Guest is a first-class mode**: the app works exactly as before without an account. Signing in, signing out and deleting the account never touch the local data, except the opt-in wipe.
- **The local wipe never touches content**: only user data (see below), never the catalog tables, `filesDir/content/`, the assets, nor the database files or schemas.
- `app/google-services.json` is committed (it is not a secret, and CI needs it to build with the `com.google.gms.google-services` plugin). **Before a public release, restrict its API key in Google Cloud Console** (Android app + SHA-1, only the APIs in use). `.gitignore` only ignores stray `google-services (N).json` copies.

**Domain (`domain/auth/`).** `AuthSession` (Guest | SignedIn(uid, displayName, email, photoUrl)), `AuthResult` (Success | RecentLoginRequired | Failure(AuthError: NETWORK, SIGN_IN_FAILED, FAILED, LOCAL_WIPE_FAILED, SERVER_DATA_FAILED, ACCOUNT_NOT_DELETED; cause)), `AuthRepository` (`session: Flow<AuthSession>`, `signInWithGoogle(idToken)`, `signOut()`, `deleteAccount(wipeLocalData, reauthIdToken)`: the token is always required), `LocalUserDataWiper` (`wipe()`), `UserDataEraser` (`eraseServerData(uid)`, the sync coordinator), `GoogleTokenResult` (failures carry `cause`), `AuthFailureLog` + `describeAuthFailure` (`LogcatAuthFailureLog` in `data/auth`), `AuthPreferences` (synchronous: `isStartChoiceMade`, `isInstallChecked`, `guestBannerDismissedAt`), `ExistingInstallMigration`, `GuestBannerRule` (guests only; after a dismissal it reappears after `REAPPEAR_AFTER_MILLIS` = 7 days, so at most once a week) and `GuestBanner` (visibility Flow + `dismiss()`, time from `WallClock`).

**Data (`data/auth/`).**
- `FirebaseAuthRepository(FirebaseAuth, LocalUserDataWiper)`: `session` from an `AuthStateListener`; the ID token becomes `GoogleAuthProvider.getCredential(idToken, null)`. `deleteAccount` re-authenticates first when given a token, maps `FirebaseAuthRecentLoginRequiredException` to `RecentLoginRequired` (once: a second one after re-authentication is a failure) and `FirebaseNetworkException` to NETWORK, and wipes only after the account is deleted (a wipe failure → `LOCAL_WIPE_FAILED`). Tasks are awaited with a private `Task.await()` (no extra dependency).
- `FakeAuthRepository` (main source set, for tests and previews): scripted `signInResult` / `deleteResults`, records calls, `SAMPLE_USER`.

- `DefaultLocalUserDataWiper`: in one transaction of the app database `training_log`, `weekly_goal`, `gym_exercise_progress`, `gym_session`, `daily_session`, `sync_outbox`, `feed_share`, `daily_progress` (new `deleteAll()` DAO queries, no schema change; never `clearAllTables` on that database, which also holds the catalog), then `ProgramDataCleaner` (every program and its progress), then `TrainingPhotoRepository.cleanUp()` (every photo file is now unreferenced). Kept in `tiominuter.db`: `exercises`, `gym_routines`, `gym_routine_exercises`, `daily_routines`, `daily_routine_exercises`. `programs.db` holds only user data (the program catalog and templates are cached in memory by `ProgramRepositoryImpl`, never stored), so clearing it is safe. Nothing the wipe clears comes from `ContentSource`, so nothing needs restoring: in the same process (no restart) the "refreshed once" flags still point at intact catalogs, Programs still shows the catalog and creating a program works. **Never add a content table to the wipe**; if one ever must be cleared, reset its repository's refresh state so the next read refreshes from `ContentSource`.

**Start and existing installs.** `TioMinuterApplication` runs `ExistingInstallMigration` right after `startKoin`, before anything opens a database: on the first launch of a version with accounts, if `tiominuter.db` or `programs.db` already exists (an update), the start choice is stored as guest (no Welcome, guest banner on Home); either way it stores `installChecked`, so a fresh install that leaves Welcome without choosing still sees it next time. `MainActivity` then picks the start destination synchronously.

**Screens.**

## Firestore

The data model and security rules (Phase 2a), used by the sync (Phase 2b, see "Sync"). Database `(default)`, region `southamerica-east1`. Full model and Room → Firestore mapping: `docs/firestore-model.md`; summary in TECHNICAL_SUMMARY §19.

- **Where.** Rules `firebase/firestore.rules`, indexes `firebase/firestore.indexes.json` (the feed's composite index and its exemptions, see below), tests `firebase/rules-tests/` (vitest + `@firebase/rules-unit-testing`, versions pinned with a lockfile), wired in `firebase.json` (`firestore` and `emulators`: Firestore 8080, Auth 9099 for the sync's emulator test; the hosting block is separate and unchanged).
- **Model.** Per person under `users/{uid}/…`: the profile doc, `trainingLog/{entryId = uuid}`, `weeklyGoals/{effectiveFromWeek}`, `dailyProgress/state` (the daily unlock: merged, never tombstoned, no `deleted` field), `programs/{programId}` + `workouts/{week}-{dayIndex}` + `completions/{week}-{dayIndex}`, plus the group index `groups/{groupId}` and counter `meta/groups`. Shared: `groups/{groupId}`, `groups/{groupId}/members/{uid}`, `groups/{groupId}/posts/{postId}`, `inviteCodes/{code}` (see "Groups" and "Feed" below). Not synced: photos and `photoPath`, gym and program slot progress, catalogs, Room ids. Every other path is denied.
- **Every model change needs a rules change and rules tests** (and `docs/firestore-model.md`). A change older apps can't read bumps `schemaVersion`.
- **`updatedAt` is always the server time** (`serverTimestamp()`; the rules require `updatedAt == request.time`), never a device clock. Conflicts: last write wins by `updatedAt`, per doc.
- **Deletions are tombstones:** the doc is replaced by `{idField, deleted: true, updatedAt, schemaVersion}` with no data. Tombstones of random ids (training entries, programs) are final; docs with natural ids (`weeklyGoals/{week}`, program `workouts` / `completions/{week}-{dayIndex}`) can be written again over a tombstone, because the same id comes back. A new collection with a natural id must use `canUpdateNaturalId`. Owner hard delete is allowed (for Delete account).
- **Firestore rules must accept every value the app can produce** (now or in any earlier version, including old rows from older Room schemas). Check against the app constraints table in `docs/firestore-model.md` before tightening a rule, and add an edge-value test. To tighten a limit, tighten the app first (for all versions in use), then the rule. `node scripts/validate_backup_against_rules.js <backup.tar>` checks a real phone backup against the rules on the emulator (counts and field names only; must report 0 rejections).
- **Groups (Phase 3a: model, rules and tests only; no app code yet).** Full model, batches, reconciliation, ranking and banner input: `docs/firestore-model.md` "Groups".
  - Signed-in accounts only (`isSignedIn()`: no guests, no anonymous Firebase users). Join only with an invite code (8 characters, `2-9 A-H J K M N P-Z`); at most **20 members** per group and **5 groups** per person; group names 1–40 characters.
  - **Reads are members-only:** a group and its member docs are readable only by its members (`exists(members/{auth.uid})`); each person can also `get` their own member doc (for reconciliation). Invite codes: `get` by any signed-in user, never `list`. Nobody lists `groups`.
  - **Each member writes only their own summary** (`members/{uid}`: name, https photo or null, `weekStartLocal` (a Monday, checked), `workoutsThisWeek` 0–100, `weeklyGoal` 1–14, `streakWeeks` 0–1000, `daysThisWeek` "1".."7" → distinct sources (≤ 4), `lastTrainedLocal`). Only these fields: never durations, notes, titles, measurements or photos. The owner may only delete another member's doc.
  - **Every group operation is ONE batched write the rules check as a whole** with `get` / `getAfter` / `existsAfter` (Spark plan, no Cloud Functions): create, join, leave, remove, transfer, regenerate code, rename, delete. `memberCount` changes by exactly ±1 together with the member doc named by `memberChangeUid`; the counter `users/{uid}/meta/groups` changes by exactly ±1 together with the index entry named by `lastGroupId`, so one group per batch. An owner leaves only with a transfer in the same batch, or by deleting the group when alone. Nobody writes another user's `users/` docs: each app reconciles its own stale index entries (removed, or group deleted).
  - Ranking (compliance, streak, name) and the banner are computed by readers, never stored. Group batches: `firebase/rules-tests/test/groupBatches.js`; tests `groups.test.js`.
- **Feed (Phase 4a: model, rules and tests only; no app code yet).** Full model, operations, expiration and budget: `docs/firestore-model.md` "Feed".
  - `groups/{groupId}/posts/{postId}`, **postId = the training entry's uuid** (one post per entry and group; deleting the entry deletes `posts/{uuid}` in each group of my index, no query). Fields: `authorUid`, `authorName` 1–100, `authorPhotoUrl` (https or null), `source`, `title` ≤ 500, `activityType` (ACTIVITY only), optional `titleKey` (see below), `durationSeconds` (int ≥ 0 or null), `dateLocal` (inside the week of) `weekStartLocal` (a Monday, checked), `createdAt` (server time), `reactions`, optional `thumb`, `schemaVersion` 1. Never the note, intensity, `refId` or `photoPath`. No `updatedAt` / `deleted`: posts are written live and hard-deleted.
  - **Members-only:** only members of an existing group read posts, post (as themselves) and react. Guests and anonymous users: nothing.
  - **Own reaction key only:** `reactions` is a map uid → code (`strong`, `fire`, `clap`, `raised`), empty on create; a member changes only their own key (`diff().affectedKeys()`), with a field-path update, nothing else in the same write.
  - **`titleKey`** (optional; older apps send none): the workout's locale-free name, so each reader names it in their own language. Strict format, only on a post of its own source, ≤ 80 characters: `gym/<routineId>` (GYM) and `daily/<dayNumber>` (DAILY), 1–9 digits without a leading zero; `program/<CODE>` (PROGRAM), `[A-Z][A-Z0-9_]*` (a `ProgramTitleCode` name). Never changes after creation (the only updates, thumbnail and reaction, change nothing else). Same format in `WorkoutTitleKey` (app) and `isPostTitleKey` (rules). **Deploy the rules before releasing an app that sends it:** older rules refuse it as an unknown field, and a refused post is never retried.
  - **The author changes only `thumb`** (set, replace, remove). **Thumb cap: bytes ≤ 65,536** (the app aims for ≤ 60 KB, ~400 px, no EXIF). `thumb` and `reactions` are exempt from indexing.
  - **Deletes:** the author (any time, also after leaving), the group's owner (while the group exists), any member once the post expired, any member for a post that doesn't exist (no-op). Leave: delete my posts first; remove member: the owner deletes their posts; delete group: posts, then members, then the group; Delete account: my posts in every group before leaving them.
  - **Expiration: 8 days after `createdAt`, computed by the rules (`createdAt + duration.value(8, 'd')`, server time only; there is no client `expiresAt`).** TTL is not available on Spark (TTL deletes need billing), so clients clean up: opening a feed deletes up to 20 posts older than 8 days, one delete each (the device clock may select one the server keeps; skip refusals), and app start does the same per group (throttled). On Blaze: a TTL policy on `posts.createdAt` with `--expiration-offset=8d` (manual), keeping the client cleanup.
  - Feed query: `where weekStartLocal == <my Monday> orderBy createdAt desc`, which needs the composite index in `firestore.indexes.json`. Reference operations: `firebase/rules-tests/test/feedOps.js`; tests `feed.test.js`.
- **Run the tests** with `scripts/test_rules.sh` (starts the Firestore emulator with `firebase emulators:exec`; Node 22+, Java 21, firebase-tools 15.34.0). CI: `.github/workflows/firestore-rules.yml` (Node 22, Java 21) on changes to `firebase/**`, `shared/**`, `firebase.json` or the script; it checks the shared fixtures are up to date and never deploys.
- **Shared test data:** the valid document of every type is defined once in `firebase/rules-tests/test/fixtureData.js` and exported to `shared/fixtures/firestore_documents.json` (`node scripts/export_fixtures.mjs`, committed; `--check` in CI). The rules tests (`fixtures.js`) and the web's Dart tests both read the JSON, never `fixtureData.js`. A model change edits `fixtureData.js`, re-exports, and keeps both green.
- **Deploying is manual**, after merging to `main`: `firebase deploy --only firestore:rules,firestore:indexes --project tiominuter-e43f7` (add `--dry-run` first to compile on the server without deploying). The CI service account only has Hosting admin, and `content-deploy.yml` deploys Hosting only.

## Sync

A signed-in account's **training log, weekly goals, programs** (with their workouts and completions) **and daily progress** are backed up to and synced with Firestore. **Room stays the only source of truth for the UI**; the UI never reads Firestore and refreshes through its existing Room flows. Guests sync nothing.

**Rules.**
- **Every synced write enqueues its change in the SAME transaction** as the row (`ChangeTracker.inTransaction` + `enqueue`): `TrainingLogRepositoryImpl` (every insert, activity edit, delete), `WeeklyGoalRepositoryImpl.setGoal`, `ProgramRepositoryImpl` (create, completions, delete). The outbox is `sync_outbox` in each database (`SyncOutboxEntity` / `SyncOutboxDao`, one row per document: collection, parentId, docId, isDelete, version, enqueuedAt). A new synced write must enqueue the same way; local wipes never enqueue.
- **Document shape = docs/firestore-model.md**, one mapper per entity (`TrainingLogDocMapper`, `WeeklyGoalDocMapper`, `ProgramDocMapper`, `ProgramWorkoutDocMapper`, `ProgramCompletionDocMapper`); `FirestoreRemoteUserData` adds `updatedAt = serverTimestamp()`, `deleted`, `schemaVersion` 1. Deletions are tombstones (`set` without merge of the id field + those three); a deleted program's children are not uploaded.
- **No ping-pong:** pulled documents are written with the sync DAOs (`AppSyncDao`, `ProgramSyncDao`), never through the repositories, so they never enqueue.
- **Pull, then push**, one sync at a time (`SyncEngine`'s `Mutex`). Pull: per collection `updatedAt >= watermark` ordered by (updatedAt, document id), paginated with an (updatedAt, id) cursor (all docs of a batch share one server time); watermarks per account and collection are saved only after a store's pull completes. Push: batches of ≤ 500; a change leaves the outbox only after its batch commits and only if its `version` didn't change meanwhile. Failure → kept, retried (WorkManager unique work `firestore-sync`, `CONNECTED`, exponential backoff).
- **Conflicts** (`SyncConflicts`): a pending local change wins over the pulled version (it is pushed afterwards and gets a newer server time), except a uuid tombstone (entry, program: deletion wins, the pending change is dropped). The same for weekly goals: **no device clock is ever compared** with a server time (a phone's clock can be wrong). With nothing pending, the remote version is applied.
- **Accounts:** guest data meeting an account (`lastSyncedUid == null`) → every local row is enqueued and the pull is full (union by id); the same account again → incremental; **another account** (`lastSyncedUid` ≠ uid) → `LocalUserDataWiper` first (automatic, no question; the other account's data stays in its own cloud), then a full download. Sign-out keeps the local data and its outbox.
- **Delete account order** (each step only if the previous one worked): 1. a **fresh Google re-authentication, always** (the confirmation asks for a token first; cancelled → nothing happens and nothing is shown, failed → the sign-in message; nothing is erased or deleted either way) → 1b. **leave every group** (`AccountGroupsCleaner`, see "Groups"; a failure → `GROUPS_FAILED`, "Couldn't leave your groups, so nothing was deleted.", nothing erased) → 2. every server document under `users/{uid}` (subcollections included, in batches; `SyncCoordinator.eraseServerData`; a failure → "Couldn't delete your backed-up data, so your account wasn't deleted.", the Firebase user is kept) → 3. the Firebase user (a failure after a successful erase, rare after a fresh re-authentication → `ACCOUNT_NOT_DELETED`, "Your backed-up data was deleted, but your account couldn't be deleted. Try Delete account again, or sign out.") → 4. the optional local wipe. **Edge case** (3 failed): the account still exists with no server data; `SyncStateStore.erasedAccount` marks it (persisted), so **no sync of it runs** (its local data and pending changes are not uploaded again, also after a restart, and "Back up now" does nothing) until the person retries Delete account (which then succeeds) or signs out (the mark is cleared when the session becomes a guest; signing in to that account again later is an explicit choice that merges the local data back).
- **PROGRAM refIds** name the program by its local id in Room ("program:12:1:0") and by its uuid in Firestore ("program:<uuid>:1:0"), converted by `ProgramRefIds` with the program feature's `ProgramRefMapper`; programs are pulled before the training log. An unknown program keeps the refId as is.
- **Triggers** (`SyncCoordinator`, started by `TioMinuterApplication`, never blocking the UI or the start): every signed-in session (sign-in and app start: the profile `users/{uid}` — name ≤ 500, https photo or null —, then a sync), 5 s after local writes (debounced outbox count), and WorkManager when offline or after a failure.
- **The daily progress is merged, never last-write-wins** (`DailyProgressSync.reconcile` in `AppSyncStore`, pulled last and always in full): the higher cycle wins, then the further day; the server ahead → the row takes it (no enqueue), the device ahead → enqueued again, no server document → uploaded, a cycle-0 state first raised to the history. See "Daily unlock".
- Not synced (by design): gym and program per-set progress, active sessions, photos and `photoPath`, catalogs and content, auth preferences, Room ids.
- Logs carry no personal data: exception classes, messages and collection names only.

**Code.** Domain `domain/sync/`: `SyncModel.kt` (`SyncCollection`, `DocKey`, `PendingChange`, `OutgoingDoc`, `IncomingDoc`, `SyncTime`, `PullQuery`, `PageCursor`), `SyncPorts.kt` (`ChangeTracker`, `LocalSyncStore`, `RemoteUserData`, `SyncStateStore`, `NetworkMonitor`, `SyncScheduler`), `SyncEngine.kt` (`SyncConflicts`, `SyncEngine`), `SyncCoordinator.kt` (`SyncRepository`, `SyncStatus`, `ProgramRefMapper`, `ProgramRefIds`, `SyncCoordinator`). ## Groups

**Rules.**
- **Every write is one batch of `docs/firestore-model.md` "Batched operations"** (`FirestoreGroupRepository`, the same batches as `firebase/rules-tests/test/groupBatches.js`); one group per batch (the counter moves by exactly 1). Reads that decide something come from the server (`Source.SERVER`). - **Delete group always in chunks:** every other member is removed one batch at a time (`removeMember`; the rules allow one removal per write), then the final batch deletes the group, its code, my member doc and index entry, counter − 1 (production limits the lookups of one batch). An owner alone leaving = Delete group.
- **Delete account order:** re-auth → **group cleanup** (`GroupAccountCleaner`: reconcile, leave member groups, owned groups with others → transfer to the oldest other member by `joinedAt` and leave in one batch, alone → delete; then the counter) → erase `users/{uid}` → delete the auth user → optional local wipe. - Sign out / account switch: groups belong to the account; only the in-memory cache and the banner dismissal are cleared (`GroupsCoordinator`).
- A weekly goal is required before creating or joining (the list asks and opens the existing goal screen).

**Screens** (MVI with `MviComposable`, stateless `*Content`, light/dark `*Previews.kt`, ViewModels in `groupsModule`). Routes: `groups`, `group_create`, `group_join`, `group_detail/{groupId}` (`NavType.StringType`; create and join are replaced by the group). - Detail (`GroupDetailViewModel(groupId, …)`): the ranking (`GroupRanking`: compliance = min(done/goal, 1), then streak, then name, then uid; a summary from another week counts 0 and shows "Not updated this week"), avatar, "done/goal", a bar, streak, a Mon–Sun strip with an icon per workout type (one TalkBack sentence), "me" highlighted; the invite code (copy/share); Leave. ## Feed

Each group has a feed of its members' finished workouts (Phase 4b; the Firestore model and rules are Phase 4a: `docs/firestore-model.md` "Feed"). Signed-in accounts in at least one group only; nothing shows for anyone else.

**Rules.**
- **Sharing is ON by default.** A workout that counts (`countsTowardGoal`, any source) recorded while signed in is queued in `feed_share` **in the entry's own transaction** (`TrainingLogRepositoryImpl` → `WorkoutShareQueue`, implemented by `RoomWorkoutShareStore`; database v10): recording, deleting the entry and changing its photo mark the row. A guest's workouts are never queued, also after signing in. The latest recorded entry of each source is announced only after the transaction commits (the daily completion screen reads it).
- **The switch is per workout** (never a global setting): `ShareInGroupsSection(entryId)` (`ui/components/share`, its own `ShareInGroupsViewModel`, through the core `WorkoutSharing` port implemented by the groups feature's `FeedShareController`) next to `CompletionPhotoSection` on the gym and program completions, `LatestShareInGroupsSection(DAILY)` on the daily completion screen, and the form's `ShareSwitchRow` in Log activity (not an unsaved change). **Nothing is posted until the one-time explanation is answered** (`FeedPreferences.isFeedIntroSeen`, per account): "OK" or "Don't share this one" (that workout off); closing it without choosing posts nothing and it shows again next time.
- **Posting** (`FeedPublisher`, started by `GroupsCoordinator`): debounced 5 s; triggers: app start, any queue change, the explanation acknowledged, a successful sync run. **One write per group, never a batch**; a group that refuses (PERMISSION_DENIED, NOT_FOUND: removed, gone) is remembered in the row and **never retried**; NETWORK / FAILED keep the row dirty for the next trigger; offline nothing is sent. A workout goes to the groups I'm in at its first post (never to a group joined later) and only while its week is current. A create whose answer was lost is recognised (the post exists and is mine), so posting is idempotent. postId = the entry's uuid; author name / photo from `MemberProfiles` (as the member summary); title = the entry's stored title (the fallback), plus the optional **`titleKey`** (`WorkoutNameResolver.titleKeyOf`: `gym/<routineId>`, `daily/<day>`, `program/<CODE>`; none for an activity, whose `activityType` readers name in their language, or when nothing is known). **Readers name a post with `GroupFeedState.nameOf(post)`** (`nameOfPost` over this device's catalogs, `WorkoutNameCatalogSource`): its key in their own language, else its title (older posts, unknown codes, a routine they lack).
- **Thumbnail cap:** the entry's local 400 px thumbnail re-encoded by `AndroidFeedThumbnailSource` with `ThumbnailFitter` (quality 60 → 30 first, then the size by 0.75, down to 64 px) **≤ 60 KB, never above the rules' 65,536 bytes** (anything larger is dropped, the post goes without it). A photo added, changed or removed later updates or removes the thumbnail of my existing posts (`FieldValue.delete()`).
- **Deleting an entry** deletes `posts/{uuid}` in every group of my index, one delete each, without reading first (a missing post is a no-op).
- **Listeners only while visible:** the group detail has two tabs, Ranking and Feed (the last one remembered per group); only the selected tab is composed, so the Feed's listener (`observeWeek`: `weekStartLocal ==` my current Monday, `createdAt` desc, 20 per page, "Load more" raises the limit) runs only while the Feed tab is visible and the screen started. Hidden posts ("Hide for me", local, per account in `group_preferences`) are filtered client-side. Thumbnails are decoded off the main thread into a small in-memory LRU (4 MB).
- **Reactions:** tap to set, the same again to remove, another to change; `update(FieldPath.of("reactions", myUid), code | FieldValue.delete())`, never read-modify-write; optimistic with rollback; offline → "No internet connection", nothing sent.
- **Moderation:** my post (menu or long press, also an accessibility action) and the owner's delete of any post ask for confirmation.
- **Cleanup (Spark, no TTL):** opening the Feed tab deletes up to 20 posts created more than 8 days ago (device clock), one by one, skipping refusals silently; at app start (`GroupsCoordinator`, throttled to once every 6 h) the same for each group of my index (`FeedCleaner`).
- **Membership sequences** (`FeedModeration`, one delete per post): leaving deletes my posts first (a failure stops the leave); removing a member deletes their posts right after the removal (a failure is logged; they expire); Delete group deletes every post, then the members, then the group; **Delete account deletes my posts in every group (all posts in a group I own alone) before the group cleanup**, so the order is re-auth → posts → groups → erase `users/{uid}` → auth user → optional wipe (a failure stops everything).
- The local wipe clears `feed_share`; an account switch drops the other account's queued rows (never posted as me).

**Code.** Core: `domain/traininglog/WorkoutShares.kt` (`WorkoutShareQueue`, `WorkoutShare`, `WorkoutShareStore`, `WorkoutSharing`, `ShareOptions`, `RecordedEntry`), `data/traininglog/RoomWorkoutShareStore.kt`, `FeedShareEntity` / `FeedShareDao`, `TrainingLogDao.getByUuid` / `TrainingLogRepository.getEntryByUuid`, `ui/components/share/`. - Animations: every catalog entry, including ids 100–127, has its GIF in `content/v1/animations/`; `ProgramCatalogValidationTest` checks that each file exists. `PENDING_ANIMATIONS` (empty) lists GIFs not delivered yet, which that check skips; the test fails when a pending file appears (remove it from the list then). Animation names from id 121 on must be `<id>_<snake_case>.gif`.
- Templates (data, not Kotlin): splits by goal, days and `focus` (missing = BALANCED; exactly one per goal × 2–5 days × focus), strength days as ordered slot patterns (muscle, preferred mechanic, candidates with gym ones first then home ones, optional TIME hold, optional `required`), prescriptions by goal and level, progression, cardio templates (outdoor run, treadmill, home circuit, low-impact variants) and impact rules.

**Focus** (`ProgramFocus(code)` in `ProgramEnums.kt`: BALANCED, LOWER_BODY, UPPER_BODY, CORE; `fromCode`; `ProgramProfile.focus`, default BALANCED). It only picks the split.
- BALANCED: the splits and day templates as they were before the focus; never change them. `ProgramBalancedRegressionTest` compares the generator output with golden files captured before the change (`src/test/resources/program_golden/<goal>_<location>.json`, 144 profiles: every goal × location × days × level × {normal, low impact by BMI, senior}). Don't regenerate the goldens to make a change pass.
- LOWER_BODY: 2 days = `FULL_BODY_LOWER_A/B` (full body with extra lower-body patterns); 3 = Lower A / Upper / Lower B; 4 = + Full body; 5 = Lower A / Upper A / Lower B / Upper B / Lower C. LOSE_FAT keeps its cardio days (3 = A, Cardio, B; 4 = Lower A, Cardio, Upper, Lower B; 5 = Lower A, Cardio, Upper, Cardio, Lower B). UPPER_BODY is the mirror (Upper A / Lower / Upper B…, Upper C).
- CORE: the BALANCED layout with `CORE_<day>` days: the day's non-core patterns, a dead-bug anti-rotation pattern third, and two `required` CORE TIME holds (plank, side plank) at the end.
- New titles `StrengthDayTitle.FULL_BODY`, `UPPER`, `LOWER`, `UPPER_C`, `LOWER_C` ("Full body", "Upper"/"Tren superior"…). Labels and descriptions: `focusLabel` / `focusDescription` in `ProgramUi.kt` (`program_focus_*` strings).
- No slot pattern targets CALVES: there is no home calf exercise, and every pattern needs an eligible candidate at HOME and GYM.

**Generator** (`domain/program/generator/`, pure, deterministic): `ProgramGenerator.generate(profile, catalog, templates)`.
- `isEligible`: canonical, available at the location (HOME: BODYWEIGHT, DUMBBELL, BENCH, NONE), no HIGH impact when low impact, no 87 for beginners or low impact. Low impact = BMI ≥ 30 or age ≥ 60; age ≥ 60 also adds 15 s rest.
- Split by goal, days per week and focus. Per strength day, the first eligible unused candidate of each pattern (preferring its mechanic) until the session size (top of the level's range for 2–3 days, bottom for 4–5); a pattern with no candidate is skipped and logged. `required` patterns are picked first and always keep their place, the others fill the rest of the session, and the workout keeps the template order (no BALANCED day has required patterns). Never the same exercise twice in a workout.
- Progression: +1 rep/week to the top of the range, then +1 set (max 5) and reps back to the bottom; holds +5 s/week; deload every 4th week when weeks ≥ 6 (sets −1, min 2; reps at the bottom; cardio × 0.7).
- Cardio: GYM → treadmill; HOME alternates outdoor run / home circuit. Low impact → brisk walk, incline walking (5 km/h, 2 %/8 %), low-impact circuit.
- Per side: `StrengthSlot.perSide` is copied from the catalog (default `false`, so older payloads decode); sets, reps and rest don't change. Home circuits never use per-side exercises (`isCircuitEligible`: circuit mechanics and not `perSide`), and the circuit candidate lists contain none.

**Persistence and repository.** Tables `programs`, `program_workouts` (one row per workout; `payload` is the domain `ProgramWorkout` as JSON), `program_slot_progress`, `program_workout_progress` (FK CASCADE). A program is generated once at creation and stored in one transaction; template changes never alter it. `ProgramRepositoryImpl` caches catalog and templates; `markSlotCompleted` completes the strength workout in the same transaction when all its slots are done; `resetWorkout` clears the slots but keeps the workout's completion; cardio screens call `markWorkoutCompleted(…, durationSeconds)`. Completions are recorded in the training history (see "Training history") and the recorded entry id is exposed by `observeCompletionEntryId` for the completion photo (see "Training photos"); the title comes from `ProgramWorkoutTitles` (`ResourceProgramWorkoutTitles`, same strings as `workoutTitle`).

**Screens** (`ui/program/`, MVI with `MviComposable`, stateless `*Content`, light/dark `*Previews.kt`, ViewModels in `programModule`): `list` (My programs, FAB, long-press delete with accessibility action; cards show "Focus: …"), `create` (form with inline validation, BMI, low-impact note, underweight warning, a "Focus" / "Enfoque" radio group between goal and location — four options with their description, BALANCED preselected, `selectable` rows with `Role.RadioButton` ≥ 48dp —, disclaimer, week-1 preview generated with the focus; Create replaces itself with the detail), `detail` ("Focus: …" first, weeks with "Week 2 · 66.7 %", Deload label, completion), `strength` (exercises, progress, reset, "Workout completed!"), `strengthexercise` (sets/rest/get-ready phases like the gym exercise; a per-side TIME set runs `PerformingTimed(LEFT)` → `SwitchingSides` 5 s with sound + vibration at the switch → `PerformingTimed(RIGHT)` → rest; a per-side REPS set shows "10 reps per side" and is one "Set done" tap), `treadmill` (segments, pause/resume/skip), `outdoorrun` (target + stopwatch, no GPS), `circuit` (rounds, work/rest). Timers use `ProgramCountdown` (end timestamp of `MonotonicTimeSource`, one job). Percentages use `formatPercent(completed, total, locale)` (one decimal, locale separator); slot summaries use `programExerciseSummary` ("Sets: 3 · Time: 40s, 40s, 40s per side" / "… por lado"; only the strength workout cards show slot summaries); exercise names use `nameEs` when the app runs in Spanish.

**Tests.** JVM: `ProgramCatalogValidationTest`, `ProgramTemplatesValidationTest` (real assets, relative paths; every goal × days × location × level × focus × impact has a split whose patterns all have an eligible candidate), `ProgramRulesTest`, `ProgramGeneratorTest`, `ProgramFocusTest` (LOWER_BODY / UPPER_BODY ≥ 60 % of each week's strength slots on their muscles, CORE ≥ 2 core slots per workout ending with two holds, no skipped pattern, cardio and prescriptions as in BALANCED), `ProgramBalancedRegressionTest` (golden files), `ProgramEntityMappersTest` (incl. focus round trip), `ProgramFormatTest`, `ProgramPerSideTextTest` (reads the real `strings.xml` files), and a ViewModel test per screen (private fakes, `MainDispatcherRule`, virtual time). Instrumented: `ProgramDaoTest`, `ProgramRepositoryTest` (in-memory DB, real assets, fake `TrainingLogRecorder`: strength auto-completion and cardio completion record; the focus is stored and drives the split), `ProgramMigrationTest` (1 → 2: a v1 program with workouts and progress survives and reads as BALANCED).

## Conventions

- User-facing strings go in `res/values/strings.xml` (English, default) **and** `res/values-es/strings.xml` (Spanish). Both files must define the same keys.
- Use plurals for "number + noun" text, e.g. "1 rep" / "10 reps". Spanish plurals also define `many`, which lint requires for `es`.
- minSdk is 24 and core library desugaring is off, so don't use `java.time`. Use `WallClock` for stored timestamps and `MonotonicTimeSource` for countdowns.
- Accessibility:
  - Icon-only buttons get a `contentDescription`; decorative icons and images use `null`.
  - State that is shown only by color or an icon is exposed with `stateDescription`.
  - Interactive elements are at least 48dp.
- Content files and animations are read only through `ContentSource` / `AnimationLocator` (see "Remote content"), never from the assets directly.
- Workout names always go through `WorkoutNameResolver` (see "Workout names"); never display a stored title directly.
- Compose theme: `TioMinuterMVITheme` (`ui/theme/`); XML theme: `Theme.TioMinuterMVI`.
- Language guidelines (neutral and inclusive, guarded by `NeutralLanguageTest`):
  - Spanish: never use gendered adjectives or participles that refer to the user (listo/a, bienvenido/a, preparado/a, cansado/a, motivado/a, comprometido/a, atrasado/a…). Rewrite with verbs, second person or nouns: "Te damos la bienvenida", "¿Empezamos?", "Tu progreso". No "@", "x" or "e" inclusive endings; keep standard, natural Spanish.
  - Motivate without blaming: no "no cumpliste", "fallaste", "perezoso", "sin excusas" / "no excuses". Never link training to appearance or weight in a negative way; BMI notes are informative and neutral.
  - **One documented exception, the brand tagline:** `home_screen_tagline` (Android; `tagline` on the web) = "No excuses — just 10 minutes a day." / "Sin excusas — solo 10 minutos al día.". It stays by the product owner's decision: it is the core motivation of the daily routine and an intentional brand line. **Do not change it without the product owner's approval.** The exception covers only that key and only its phrase: "sin excusas" / "no excuses" stays banned in every other string, and every other rule still applies to the tagline.
  - English: no gendered terms for the user ("guys", "bro", "man up", "beast mode"); same tone rules.
  - `NeutralLanguageTest` (JVM) reads both `strings.xml` files and fails on whole-word matches of the denylist (the tone list includes "sin excusas" and "no excuses"); legitimate uses go in its documented allowlist, which maps a key to the only denylisted words it may contain (every other word is still checked there): `welcome_title` → "bienvenida" ("Te damos la bienvenida", where "bienvenida" is the noun) and `home_screen_tagline` → "no excuses" / "sin excusas" (the tagline above). It also proves the phrase fails in any other string. The web's `test/ui/l10n_test.dart` has the same allowlist for its `tagline` key.
- ViewModel tests use private fakes inside the test class. Timer tests use `testutil.MainDispatcherRule` (`runTest` shares its scheduler) and a `MonotonicTimeSource` that reads the scheduler's virtual time.
